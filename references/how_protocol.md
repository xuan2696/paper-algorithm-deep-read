# How：从原图走通算法

写作目标是让读者能对照原图说明算法怎样运行。结合全文补足图中省略的关系，不能把图注扩写几句就当作算法解释，也不能把论文改写成与主线无关的基础知识教程。

## 1. 建立方法全貌

先用一段话给出：

- 一次任务接收什么输入、在什么条件下工作；输入是原始数据、观测、状态、序列还是待求解实例。
- 总体经过哪些关键变换，哪些环节体现本文贡献。
- 算法直接输出什么，以及如何转成任务结果。例如动作价值向量、动作分布与实际执行的动作不是同一个量。

顺序遵循计算流程。论文先介绍损失、后介绍网络时，可以调整讲解顺序，但不能改变原方法的依赖关系。

在工作索引中记录核心模块及其 `input`、`operation`、`output`、`evidence`、`unknowns` 即可；可直接扩展 `paper_index.json.method_modules`。该记录用于查漏，不要求报告逐字段复制。

## 2. 逐图与逐子图解释

方法图包括整体网络、局部模块、算法流程、机制示意、训练与推理框架。先看总览，再在对应步骤展开局部细节，不按图号机械排列。

每张插图：

1. 图前用一句话指出它回答的技术问题、推荐的读取方向和当前关注的分支。
2. 图后沿真实模块与连线解释输入、计算、输出和下一站，使用原图标签帮助定位。
3. 分别解释具有独特信息的 `(a)/(b)/(c)`、放大框、重复层、并行支路及回路；说明子图如何接在一起。
4. 将图中没画出的关键步骤从正文、伪代码和附录接回来，说明补充内容的来源。

总览与局部图经常互补，不能因“都讲注意力”就只留总览。重复图仅在保留图完整覆盖其独特技术信息时省略。背景图只解释理解本文所需的部分，不与创新模块等量展开。合并提取的原图保持原样，说明正在解释左侧、右侧或相应子图。

箭头需要分清特征传递、消息通信、条件控制、历史状态、损失监督、参数更新和环境反馈。颜色、实线/虚线或阴影区域只有在图例/正文支持时才能赋予特定含义；不能把所有线都理解为前向计算，也不能看到虚线就断定停止梯度或反向传播。

## 3. 核心模块的解释颗粒度

每个核心模块要能回答下面的问题，采用连贯段落或少量步骤，不强制大表格。

| 要素 | 需要交代的内容 |
| --- | --- |
| 输入 | 来自数据、上一模块、历史状态还是训练标签；各变量表示什么；必要的个体/时间索引。 |
| 内部操作 | 怎样编码、筛选、计算权重、聚合、拼接、优化或求解；不能只说“提取特征”“融合信息”。 |
| 输出 | 表示什么、送到哪个模块、怎样影响最终任务；区分特征、分数、概率和决策。 |
| 形状 | 有助理解时说明维度/数量变化及其依据；只写论文披露或可核实推导的部分。 |
| 设计作用 | 它针对 Why 中的哪个不足，机制为何可能起作用；作者理由与读者解释分别标注。 |

若常规模块内部不是本文重点，简要交代其实际操作及接口即可；创新模块、关键约束和易混淆的连接要展开到能解释工作机制的程度。

### 维度与实现细节

- 论文明确给出数值时引用来源。只确定符号关系时先定义符号，说明是用于解释的记号，不暗示原文报告了具体大小。
- 不知道维度时照样解释语义与关系，并在相关处标明未知。不能为了凑“完整架构”猜隐藏宽度、层数、head 数、激活函数、归一化或参数共享。
- 某附录表给出一个 hidden size，不等于能据此确定所有中间张量的形状。
- 图画出 Attention，不意味着完整采用标准 Transformer；图画出 GRU，不意味着已经披露输入拼接、序列采样、隐藏状态重置或截断反传策略。
- 区分共享参数和多个网络实例；重复画几个模块不自动表示独立参数，也不自动表示共享。

## 4. 把公式接回图和步骤

选择理解机制、目标函数和关键约束所必需的公式，核对符号定义及上下文。每个核心公式说明：

- 对应图中哪个模块、哪条边或哪个算法步骤。
- 输入量从哪里来，怎样运算，得到什么量，随后怎样使用。
- 关键符号、求和/归一化的范围、时间或对象索引，以及影响理解的条件。
- 为什么这一步服务于设计目标；没有作者解释时标为读者理解。

不要只列公式再逐个翻译字母。保留原式编号；等价改写标明“将原文式 (x) 等价写为”，解释性简化标明省略了什么。读者推导要给依据和适用范围，不能写成作者证明。无法可靠辨认公式时，解释已确认的机制并说明缺失，不拼出一个看起来合理的版本。

例如，注意力应解释谁产生查询、对谁打分、在哪个集合归一化、权重乘到什么内容、多个头如何汇合；原文未给出其中某项就明确未知，不能直接套入标准 Q/K/V 管线。

## 5. 分别走通训练与推理

有学习过程时，至少走通下面两条路径；相关细节在正文、伪代码、实验设置和附录之间交叉核对。

**训练路径：** 样本/轨迹如何获得 → 模型接收哪些训练信息 → 预测/价值/策略如何产生 → 标签、奖励或目标如何构成学习信号 → 哪些参数怎样更新。目标网络、冻结分支、交替优化和阶段切换仅在论文提供依据时说明。

**一次推理路径：** 实际获得的信息 → 保留的模块及初始化/历史状态 → 前向计算或在线迭代 → 输出选择/解码/后处理 → 最终任务行为。指出只在训练使用的部件，不能把损失、训练标签或全局特权信息默认搬到推理中。

对于多智能体/强化学习论文，额外核对：

- 全局状态、局部观测、历史和通信消息分别由谁获得。
- 分散执行是否仍需在线通信；不要把分散决策解释成没有消息交换。
- 每个体的价值/策略怎样连接联合目标；集中训练组件是否在执行时保留。
- 探索时的采样与评估时的动作选择；奖励属于环境定义还是算法输出。

这些是条件检查项，不将每篇论文都套成强化学习网络。非学习算法相应说明初始化、迭代更新/搜索、约束处理、收敛或停止条件和最终解；不存在训练阶段就直说，无需虚构训练/推理之分。

必要时给一段“单样本/单时间步走读”或简短忠于原文的伪代码，把已有解释串成闭环。不要借伪代码补全论文未披露的实现。

## 6. 全文补充与证据边界

图是导航，不是唯一信息来源。联查任务定义、背景中被方法引用的定义、方法正文、算法框、实验实现设置、附录和补充材料。只使用实际提供或已取得的材料，不声称读过未获得的补充文件。

- 作者明确说明的设计原因按作者观点转述；由计算关系得出的直觉标“我的理解/推断”，给出依据。
- 图、公式、伪代码或正文不一致时，定位冲突并保留歧义，说明当前解释依据。不能默默拼成一个更自洽却非原文的方法。
- 实验有效不能单独证明每项设计理由；模块的因果贡献需要对应消融或其他证据。
- 不默认读取、运行或核验作者代码。用户要求复现或代码核对时，区分论文描述和特定代码版本的实现，分别给出处；静态读取代码不等于运行验证。
- 缺失细节在相关模块附近说明；必要时在 How 结尾用短段归纳影响理解/复现的缺口，不另立一章审计清单。

## 7. 交付前的语义复核

将下面的复核结果保存在工作索引/笔记，不复制进正文：

1. 读者能否从任务输入走到实际输出，核心量没有突然出现或消失？
2. 每个独立方法图、关键子图和贡献模块是否有实质解释，能对照原图定位？
3. 公式是否解释了实际操作并接回流程，而非只翻译符号？
4. 训练和执行/在线求解各自需要什么信息、怎样运行，是否说清？
5. 设计理由、已报告实现、读者推断和论文未知是否容易区分？
6. 所有关键技术事实是否可定位到已读材料，没有从常见实现补造细节？

不能用字数、插图数量、出现“输入/输出”几个词或验证器通过代替这些判断。
