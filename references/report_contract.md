# 报告结构与验收

## 五段叙事

完整报告只有下列五个二级章节，顺序固定。可在 How 内使用三级标题；术语、公式和图片在相关位置解释，不新增公式集、创新点汇总、背景百科或自检章节。

```markdown
# 论文精读报告：论文标题

## 1. What：做了什么

## 2. Why：为什么做

## 3. How：如何实现

## 4. Experiment：如何证明有效

## 5. Question：评价与疑问
```

其他语言保留序号和 What/Why/How/Experiment/Question 关键词，翻译说明文字。标题后可加简短作者/年份/来源信息，仅写已确认的内容。

**What：** 以任务、输入输出、关键做法和实际贡献说明作者完成了什么。避免“提出一个新框架，效果更好”这种泛化概述，不提前重复全部技术细节。

**Why：** 指出作者针对哪些既有方法、在什么条件下的哪些不足。连接观察、设计目标与思路；启发没有写明时不能代作者补写。

**How：** 使用 `how_protocol.md` 的逐图数据流讲解。建议组织为全局输入输出与架构、按流程展开的核心模块、训练/优化、推理/在线求解与输出。根据实际算法调整三级标题，创新模块、关键子图和核心公式是重点。没有固定字数上限，不为贴近原版短篇幅删掉独立机制。

**Experiment：** 从 Why 中的目的选择证据，串联“主张 → 实验设置 → 关键结果 → 支持程度与边界”。解释必要的数据划分、相关基线、比较条件、指标方向和可核实数值；区分百分点与相对提升，没有统计检验不能称统计显著。消融、泛化和成本是否需要展开由作者主张决定，不机械遍历所有实验。

**Question：** 区分作者自述局限、实验可见现象和读者判断。批评须有具体依据，提出能检验疑问的对照/补充实验。未报告某项信息可视为披露不足，但不能据此断言作者没有实施该步骤。不要对所有论文套用“数据少、缺乏真实场景”等结论。

## 写作颗粒度

How 通常最长，Experiment 次之；其余三节简洁而具体，不设固定比例。把重复背景、同一贡献的反复解释和无关复现细节删去，为真正的算法解释留篇幅。

以连贯段落为主，必要时用步骤、小表或简短伪代码辅助。不能把正文写成每个模块重复若干字段的表格；也不能以公式数量、段落长度或插图数量代替机制解释。基础术语首次出现时就地简释，服务于理解本文。

## 证据、数学与图片

- 重要事实及关键技术步骤附原文位置，例如 `(Evidence: Sec. 3.2, Fig. 2, Eqs. 4–5, PDF p. 6)`。每节有证据；一处章节级锚点不能为本节所有未核实细节背书。
- 数值、超参数、维度及结论只写已确认的内容。区分原文结论、实验观察、等价改写与读者推断，解释性推导须标明依据。
- 页码按 PDF 页序；若同时使用印刷页码，显式区分。
- 行内公式用 `$...$`，行间用独占行的 `$$`；不使用反引号、代码块或其他数学定界符包装公式。
- 仅嵌入 manifest 中确认为有效、已经预读并在计划中选定的 pdffigures2 图片，使用相对路径。路径存在不证明图注/裁取内容正确。

## 两层验收

先进行语义复核：按 `how_protocol.md` 检查算法是否可追踪，再核对贡献、动机、实验和独立评价是否由原文支持；检查每个独立方法图是否有实质讲解，是否保留了关键未知与图文冲突。

然后运行：

```text
python "<skill>/scripts/validate_report.py" "<paper-output>/report.md"
```

验证器检查五节、证据锚点的存在、数学格式、manifest、全量图表分析状态、全局选图、去重代表、插图路径与章节覆盖。它不检查视觉分析是否真实、证据位置是否正确、算法解释是否充分或科学结论是否成立；通过后仍需读者依据原文复核。

未完成图像核查或缺少原文时明确哪些部分尚未完成，不将部分成果描述为完整精读。用户只要一幅图或 How 的局部补讲时，不为通过完整报告验证器擅自补写其余章节。
